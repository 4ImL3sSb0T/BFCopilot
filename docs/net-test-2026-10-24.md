# 2026-10-24 通信压力与可靠性台架记录

## 环境与固件

- 开发板：ESP32-C6FH4，USB Serial/JTAG `COM4`，ESP-IDF v6.0.2。
- 链路：Windows 热点 `192.168.137.1`，开发板 `192.168.137.40`。
- 测试端口：TCP 服务端 3333、UDP 3334、板端 TCP 客户端目标 3335。
- 四个 TCP 会话槽中一个预留给客户端，服务端压力使用三个槽。
- 固件为当前 bring-up 测试应用，舵机电源关闭，其他 BSP 自检仍运行。
- 烧录镜像：`build/BFCopilot.bin`，1,037,728 字节。
- 镜像 SHA-256：`dd7d898517f50167bf145739bc6377353ffcccfd98ed32e7c79945c101293433`。

## 发现与修复

1. TCP 服务端测试任务跳过 `connected=false` 的会话，导致 BSP 为调用方保留的未读尾部无法排空、槽位不能复用。修改前异常断连测试约 1.7 秒即失败，错误为 `board closed the TCP connection`。现改为有界地读取并丢弃断连尾部。
2. 板端 TCP 客户端也提前跳过断连会话。电脑回复第五帧后关闭连接时，最后一帧回显仍在接收缓冲，客户端成功计数停在 4，预留槽无法重连。现允许继续校验断连尾部，仅在连接有效时发起新发送。
3. 原 UDP 可靠性测试会重试、载荷每 256 包重复，还会忽略同长度的错误回显。现每包仅发送一次，带 32 位序号并验证全部字节。
4. 原压力测试先执行 TCP 再执行 UDP，且重复/其他 worker 的有效载荷可能被计为成功。现同时施压，区分唯一回显、损坏、重复、乱序、本机拥塞和端到端丢失。
5. TCP 整帧接收改用统一截止时间；板端客户端覆盖整个测试过程，并用十秒进展超时检测停滞。每十秒记录堆和两个任务的栈余量，串口检测复位、panic、看门狗及堆损坏。

服务端和客户端的问题发生在板端测试消费者；BSP 保留断连尾部是既有接口约定。原有未提交的网络接口修改予以保留。

## 复现与验收

完整参数、报告字段及各模式语义见 [网络测试说明](net-test.md)。本次持续测试的参数：

```powershell
uv run --project tools python tools/bf_net_test.py --host 192.168.137.40 --mode all --duration 300 --tcp-workers 3 --udp-workers 2 --udp-burst 1 --udp-rate 50 --stress-payload-size 128 --reconnects 1000 --reliability-messages 3000 --max-loss 0 --stress-max-loss 0.01 --fault-rounds 100 --client-listen-port 3335 --client-reconnect-every 5 --serial-port COM4 --serial-log .cache/net-soak-final-20261024.serial.log --report-json .cache/net-soak-final-20261024.json
```

UDP 可靠性要求零丢失；持续压力要求回显丢失不超过 1%，本机无发送拥塞，TCP 无错误、UDP 无损坏/重复，测试结束仍能收发。板端客户端每五帧断开一次，必须持续恢复，不能仅以开始时的少量成功帧判定通过。

串口有 42 次健康样本：当前空闲堆采样范围 227,832–246,964 字节，结束样本 244,608 字节；历史最低空闲堆 177,808 字节。最大连续空闲块最低 208,896 字节，结束为 221,184 字节。测试任务最小栈余量 3572 字节，网络任务 2072 字节。本次未见持续下降或栈耗尽，但这些采样不能排除更长时间的泄漏。

失败时没有 Wi-Fi 断连事件，且已有代码关闭 modem sleep。UDP 同期出现秒级往返延迟，说明存在链路或调度停顿；仅凭当前日志不能把原因归到热点、无线干扰、主机或协议栈中的某一层。该配置尚不能宣称满足飞控通信的持续可靠性要求。

原始结果：`.cache/net-soak-final-20261024.json`；串口：`.cache/net-soak-final-20261024.serial.log`。修改前的槽位耗尽证据为 `.cache/net-baseline-fault.json`。早期 `.cache/net-soak-20261024.json` 在发现客户端停滞后中止，保留为诊断材料，不作为完整测试通过证据。

最大报文测试期间并行 ICMP 130 次，127 次回应，3 次丢失；成功回应最小/最大/平均 RTT 为 0/97/19 ms。ICMP 与 UDP 的损失差异提示数据报负载或缓存压力显著，不能直接把全部损失解释成无线断连。

两轮串口均未发现复位、panic、看门狗、堆损坏或板端客户端数据错误。最大报文轮历史最低空闲堆为 192,356 字节；过载轮为 134,536 字节，最小网络任务栈余量 2064 字节。未以增加缓存、延长超时或重发来把过载改判成功。

原始结果分别在 `.cache/net-max-payload-20261024.json`、`.cache/net-overload-20261024.json`，对应 `.serial.log` 保存串口，`.cache/net-max-payload-20261024.ping.log` 保存 ICMP。最大报文轮暴露了恢复检查短路的问题：脚本现会分别保存并执行 TCP/UDP 恢复检查，即使其中一项失败；这一行为有主机回归覆盖。板端客户端出现后台错误时，脚本也会保留已收帧数、连接数及具体错误。

当前结果说明：普通短时回显、资源复用和断连处理已修复并通过对应场景，但持续延迟、最大报文 UDP 承载和过载下的 TCP 服务质量仍未达标。继续优化前应明确实际报文长度、发送频率、允许丢失率及截止时间，并针对失败场景补充抓包和队列丢弃/发送耗时观测。

## 最终功能回归

最后使用当前脚本完整运行短时流程：100 次 TCP 重连、100 包 UDP 可靠性、10 次异常断连，以及三个 TCP 加一路 20 包/秒 UDP 的 20 秒混合压力，载荷 128 字节。总耗时 30.758 秒，判定 PASS：TCP 完成 2620 帧/335,360 字节，UDP 400/400 回显，客户端跨重连回显 25 帧，结束后 TCP/UDP 检查通过。原始结果为 `.cache/net-final-check-20261024.json`，串口为同名前缀的 `.serial.log`。这只确认低负载功能回归，不能代替前述长时和高负载失败结果。

## 验证边界

本记录是有限时间、单板、单热点、舵机关断条件下的通信台架验证。回显丢失不能区分上行、板端缓冲和下行；往返延迟不是本地控制环执行时间。未执行 24 小时运行、射频断网/热点重启、供电扰动及执行机构工作时的干扰测试，也没有根据未知控制周期宣称满足飞行实时性。
